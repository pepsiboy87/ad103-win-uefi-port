# 64G 内存 + RTX 4080，我跑通了 125B 大模型：60–70 token/s 实测与 7 个坑

> 先说结论：不是「能不能跑」的问题，是「用哪套参数跑」的问题。
> 同一台机器，默认参数 3 token/s，调对之后 60–70 token/s，差 20 倍。

---

## 一、实测数据（不是跑分，是真实任务）

硬件：RTX 4080 16G（已解锁 fp16/bf16）+ 6 核 12 线程 + 64G DDR4-2667 + 2TB NVMe
模型：Qwen3.8-Flash-Next IQ2_XS（68GB，512 专家 MoE，每 token 激活 10 个）
引擎：Strata 0.2.11 / engine 0.1.57 CUDA 13

| 任务 | 结果 | 速度 |
|---|---|---|
| 公文写作 | 格式合格，略套话 | 90.7 tok/s |
| 人口数据计算（三组降幅） | 6.04% / 4.68% / 10.44%，全对 | 77.0 tok/s |
| 应用题（两元一次方程） | 17 间房 / 86 人，正确 | 72.4 tok/s |
| Python 代码生成 | 逻辑对，但交付形式会崩 | 73.8 tok/s |
| 长文摘要（400 字→200 字） | 数据全保留 | 82.0 tok/s |
| 2.6 万字检索（32K 上下文） | 3 个埋点全中 | 62.7 tok/s |
| 6 万字检索（64K 上下文，4 万 token） | 3 个埋点全中，含中间位置 | 64.5 tok/s |
| 图像读表（4 行数据） | 数字全对 | 64.0 tok/s |
| 10 连发稳定性 | 10/10 通过 | 平均 64.6 tok/s |

**关键指标**：
- 提示词处理 2,147–2,254 token/s（4 万 token 材料，18 秒读完）
- 连续 10 次请求，GPU 温度 49→59℃，没有降频
- 显存 15.5/16 GB（吃满），内存 46.9/64 GB
- 引擎自报：专家缓存命中率 88%，推测解码草稿命中 13/27

## 二、为什么别人说跑不动，我能跑起来

网上流传的「64G 内存跑 125B 只能 2–3 token/s」，通常踩了三个坑：

1. **模型放机械盘**。125B MoE 每个 token 都要换专家，机械盘随机读 180MB/s，直接跪。我放 NVMe（3.5GB/s），这一步就是 3–5 倍。
2. **没开专家缓存**。llama.cpp 默认不保证热专家常驻显存。Strata 的调度器做到了 88% 命中——绝大多数 token 根本不需要读盘。
3. **没开推测解码**。小模型先猜几个词，大模型只做验证，命中率 48% 时速度提升明显。

**顺带纠正一个误解**：把显卡 fp16 算力从 91.9 拉到 174.4 TFLOPS（+90%）确实有用，但 MoE 推理的瓶颈是内存带宽和专家调度，不是纯算力。证据：满载推理时 GPU 功耗只有 18W、温度 59℃——它大部分时间在等数据，不是在算。

## 三、我的启动参数（逐条解释）

```
strata launch --model-path F:\AI\Strata\models --model iq2_xs \
  --context 64k --kv q4_0 --vision cpu --parallel 1 \
  --tune skip --access local --port 8080 --no-tui
```

| 参数 | 作用 | 为什么这么选 |
|---|---|---|
| context 64k | 上下文长度 | 装得下 4 万字材料；日常用 32K 更省显存 |
| kv q4_0 | KV 缓存 4bit | 对话记忆省一半内存 |
| vision cpu | 图像识别走 CPU | 显存 <24G 时的默认最优，不跟模型抢显存 |
| parallel 1 | 单并发 | 个人使用，多并发只会互相拖慢 |
| tune skip | 跳过自动调参 | 首次启动更快；稳定后可 retune tune quick |

## 四、七个坑（每个都真踩过）

**坑 1：模型文件名必须用官方名**
IQ2_XS-00001.gguf 不认，必须叫 Qwen3.8-Flash-Next-GSQ-RCO-IQ2_XS-00001-of-00002.gguf。省空间的解法是硬链接：New-Item -ItemType HardLink，两个名字指向同一份数据。

**坑 2：这个模型默认先思考再回答，思考内容也吃 token**
max_tokens=900 时，900 个 token 全被思考过程吃掉，正文返回空，finish_reason 为 length。看起来像模型不会做题，其实是参数问题。解法：请求里加 chat_template_kwargs 的 enable_thinking=false，或把 max_tokens 提到 2000 以上。

**坑 3：aria2 下 hf-mirror 的文件会假完成**
它连到 hf-mirror 的 CAS 节点后 16 连接全卡住，40 秒 0 字节，但文件长度会跳（稀疏写入），看起来下了 20GB，实际全是空洞。必须用 SHA256 校验，别信文件大小。

**坑 4：gh-proxy 对 Range 请求不稳定**
多线程分段下载引擎包，有连接会忽略 Range 直接返回整份文件，拼出来的 tar 解压报 truncated。大文件走官方下载器，别图快。

**坑 5：单连接只有 2–4 MB/s，分段并行能到 57 MB/s**
hf-mirror 单连接被限速。同一个文件切 20 段、8 并发，实测聚合 57MB/s，66GB 二十分钟下完。

**坑 6：显卡可能只跑在 PCIe x8**
引擎自检会报：PCIe 3.0 x8（显卡支持 4.0，主板 3.0）→ 到显卡约 8GB/s。长提示词时专家要过 PCIe 搬运，插槽插错或被 M.2 占用会明显拖慢。

**坑 7：模型比内存大，不等于跑不了**
68GB 模型不等于需要 68GB 内存。这个模型分两个分片：分片 1（39GB，含全部专家）常驻内存和显存；分片 2（29GB，是 n-gram 查表）留在 SSD 按需读取。所以 64G 内存够用（官方说法：专家 35.5GB + 系统 10GB）。

## 五、什么时候用它，什么时候别用

**放心用：**
- 读几万字材料、政策文件、报表，抽取要点（2,254 token/s 预填，4 万字 18 秒）
- 数据核算、百分比、趋势判断
- 看表格截图、票据、扫描件（OCR 级别准确）
- 批量起草、摘要、翻译
- 涉密或隐私材料（全程不出本机）

**别指望它：**
- 直接交付代码。实测它写的函数逻辑全对（我跑了 6 组用例全 PASS），但把一行注释和赋值挤到同一行，导致整段跑不起来。生成代码必须人工跑一遍。
- 正式公文定稿。套话明显多于闭源大模型，适合出初稿，不适合直接签发。

## 六、成本

| 项目 | 本地 | 云 API |
|---|---|---|
| 设备 | 已有（4080 + 64G） | 无 |
| 单次调用 | 0 元 | 按 token 计费 |
| 66GB 材料读一遍 | 0 元 + 18 秒 | 数元 + 网络等待 |
| 数据 | 不出本机 | 出网 |

结论：把读材料这种最费 token 的活放本地，把写成品交给云模型，是目前最省钱的分工。

## 七、一句话总结

> 125B 模型在 64G 内存 + 16G 显存的机器上，能跑到 60–70 token/s，前提是：模型放 NVMe、开专家缓存、开推测解码、调对思考模式开关。它读得又快又准，算得也对，唯独写字毛糙。
